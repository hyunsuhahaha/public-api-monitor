# 대시보드 응답 시간: 2초 → 7ms

운영 데이터가 몇 시간치일 때는 문제가 보이지 않았다. 그래서 운영 규모의 한 달치 데이터를 만들어 미리 쟀다.

## 측정 방법

- 데이터: API 45개 × 지역 2곳 × 5분 간격 × 30일 = 원시 확인 약 78만 건, 판정 약 39만 건 (`internal/web/bench_test.go`가 한 번 만들어 캐시)
- 실행: `go test ./internal/web -run x -bench Overview -benchtime 5x`
- 환경: Ryzen 5 7535HS, WSL2, 순수 Go SQLite(modernc)
- "캐시 없음"은 매번 새 서버로 요청한 값, "캐시"는 같은 서버에 반복 요청한 값

## 결과

| 요청 | 처음 | 시간별 롤업 | + 합친 행만 읽기 | + 최신 상태 테이블 (최종) | 캐시 적중 |
|---|---|---|---|---|---|
| overview 24h | 230ms | 227ms | 186ms | **7ms** | 12µs |
| overview 7d | 604ms | 244ms | 165ms | **44ms** | 41µs |
| overview 30d | 2,069ms | 521ms | 284ms | **171ms** | 20µs |
| series 30d | 859ms | 77ms | 40ms | **40ms** | – |

## 무엇이 느렸고 어떻게 고쳤나

추측으로 고치지 않고 단계마다 `go test -cpuprofile`로 확인했다.

1. **긴 기간을 원시 행으로 계산했다.** 30일 overview가 78만 행을 읽고 Go에서 정렬해 백분위를 구했다.
   → 쓸 때마다 **시간별 롤업**(API·지역·시간당 1행)을 갱신한다. 판정 개수와 응답 시간 히스토그램(19개 구간)을 담는다. 7일·30일과 24시간(1시간 구간)은 롤업으로 계산한다. 백분위는 Prometheus 히스토그램처럼 구간 안 선형 보간 추정치다.
2. **overview가 지역별 행까지 읽었다.** 프로파일상 시간의 84%가 롤업 행 읽기였다.
   → 쓸 때 모든 지역을 합친 `ALL` 행도 갱신한다. overview는 판정 행과 `ALL` 행만 읽는다. 지역별 행은 상세 패널(series)만 쓴다.
3. **모든 요청이 "API별 최신 판정·최신 확인"을 `MAX … GROUP BY` 조인으로 찾았다.** 프로파일상 남은 시간의 90%였다(최신 확인 67%, 최신 판정 23%).
   → 같은 트랜잭션에서 갱신하는 `latest_checks` / `latest_verdicts` 테이블을 둔다. 원격 감시기 결과가 늦게 도착해 순서가 바뀌어도 더 최신 값만 반영한다. 읽기는 행 몇 개 조회로 끝난다.
4. **대시보드는 30초마다 다시 요청한다.**
   → 응답 전체를 기간별로 캐시한다. 1시간은 15초, 6시간·24시간은 30초, 7일은 2분, 30일은 5분이다. 열린 대시보드가 여러 개여도 계산은 한 번이다.

기존 데이터베이스는 열 때 롤업과 최신 상태 테이블을 한 번 채운다(`backfillRollups`, `backfillLatest`).

## 대가

- 확인 1건을 쓸 때 쓰는 행이 늘었다: 원시 행 1 + 최신 상태 1 + 롤업 2(지역, ALL). 5분마다 45건이라 부담은 없다.
- 24시간 이상 기간의 응답 시간 백분위는 추정치다(구간 경계 ±구간 폭). 1시간·6시간은 원시 값으로 정확히 계산한다.
- 롤업은 원시 데이터 보존 기간의 4배까지 둔다(행이 작아서 몇 달치 추세를 싸게 남긴다).
