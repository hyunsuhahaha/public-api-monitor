# 포스트모템: 배포 직후 시작 단계 교착으로 감시 10분 중단

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-10-19 00:45 ~ 00:55 (KST), 약 10분 |
| 심각도 | SEV-2 (감시 전체 중단, 데이터 유실 없음) |
| 영향 | 집 PC 운영 인스턴스(home-wsl)가 공공 API 45개를 확인하지 못함. 상태판 응답 없음 |
| 원인 커밋 | `af9f58a` (시간별 롤업 도입) |
| 수정 커밋 | 이 문서와 같은 커밋 |

## 요약

성능 개선 배포 후 재시작한 인스턴스가 준비 상태(`/readyz`)가 되지 않았다. 프로세스는 살아 있었지만 CPU 0%에 로그도 없었다. SIGQUIT으로 고루틴 덤프를 떠 보니 `store.Open` → `backfillRollups`에서 멈춰 있었다.

기존 데이터를 시간별 롤업으로 한 번 옮기는 코드에서, 트랜잭션을 연 뒤 문장 하나를 트랜잭션(`tx`)이 아니라 DB 핸들(`s.db`)로 실행했다. 이 저장소는 SQLite 연결을 하나만 쓴다(`MaxOpenConns(1)`). 그래서 그 문장은 트랜잭션이 쥔 연결을 영원히 기다렸다.

## 왜 테스트와 벤치마크가 못 잡았나

백필은 **"원시 데이터는 있는데 롤업 테이블은 비어 있는" 데이터베이스**에서만 돈다. 그런데 테스트는 빈 DB에서 시작했고, 벤치마크 DB는 새 코드로 처음부터 썼다(롤업이 쓰기와 함께 채워짐). 실제 운영 DB만 이 경로를 탔다.

## 잘 된 것

- 데이터 유실은 없었다. 확인 결과는 메모리에만 있다가 사라진 게 아니라, 애초에 확인이 멈췄다.
- 고루틴 덤프 한 번으로 정확한 줄을 찾았다.

## 잘 안 된 것

- 배포 후 `/readyz`를 바로 확인하지 않아서 발견까지 8분이 걸렸다.
- 이 인스턴스에는 아직 Prometheus 알림이 붙어 있지 않다. 붙어 있었다면 `PamonTargetNotChecked`(10분 동안 확인 없음)가 울렸을 것이다.

## 재발 방지

| 조치 | 상태 |
|---|---|
| `tx`로 수정 | 완료 |
| "옛 DB를 열면 백필하고 10초 안에 끝난다" 테스트 (`TestBackfillOnOpen`) | 완료 |
| 재시작 스크립트가 `/readyz`를 기다리고, 시한 안에 안 되면 실패로 끝나게 하기 | 예정 |
| 마이그레이션은 운영 DB 사본으로 먼저 열어 보는 단계를 배포 절차에 넣기 | 예정 |
| SQLite 단일 연결에서 트랜잭션 중 `s.db` 사용을 잡는 린트(또는 함수가 `execer`만 받게 하기) | 검토 |

## 교훈

데이터 마이그레이션은 **"새 코드로 만든 데이터"가 아니라 "옛 코드가 만든 데이터"** 로 테스트해야 한다. 그리고 배포는 준비 상태 확인까지가 배포다.
